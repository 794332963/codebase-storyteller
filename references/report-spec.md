# 报告规格与详细度标准

## 目标读者与完成定义

读者是从未接触目标代码的后端开发者。业务视角报告读完后，读者应能独立串讲业务主干、定位代码入口、理解状态与字段如何变化，并在常见故障发生时知道先从哪里查。架构视角报告读完后，读者应能从公开入口顺着主干调用读懂核心抽象、关键数据结构、设计模式和扩展边界。

图不能替代解释，文字也不能替代结构图。删掉图后，文字仍要能讲清主干；删掉文字后，图仍要能展示关系和路径。

## 证据表达

每个关键结论必须可在方法速查表、模块深挖或排障入口中回溯到 `file:line`。不要为此在每张图下重复摆放证据链接。使用下列标签：

- `事实`：代码直接定义、调用或写入。
- `代码推断`：从多处代码行为可合理得出，但未被注释或显式规则声明。
- `证据不足`：在本次目标分支和纳入范围内无法确认。

禁止用完整的业务语言掩盖证据不足。遇到冲突实现，分别列出冲突位置和影响。

## 深度与覆盖闸门

本节是业务视角与架构视角共同继承的顶层要求，不因仓库数量、目标数量、语言或报告篇幅而失效。真实性优先于压缩篇幅；小范围目标保持适度，不用无关细节注水。

1. **单元穷尽覆盖**：业务视角的每条核心链路、每个核心实体、每个核心方法，以及架构视角的每个核心机制、主干、目标，均为一个分析单元。每个单元必须覆盖其完整实现面：构成它的关键类型、方法、真实分支、相关包/文件、存储/外部边界与跨仓库边界。跨文件机制要解释整体职责和关键成员，不能只读一个文件就概括整个 package 或模块。
2. **反浅采样与覆盖诚实**：形成结论前先阅读所选业务或目标在所有涉及仓库中的全部相关文件。阅读范围如实列出实际覆盖规模，并为每个核心单元列出真正涉及的核心文件与符号集合；不得只抽样少量文件或方法就结束。
3. **大范围单份保深度**：开始生成前评估核心单元、跨仓库边界和相关文件范围，但无论范围大小都只生成一份完整报告。报告体量随范围增长，每个单元独立成节；必须同时保持完整实现面、图表可读性和固定质量门槛，不得默默缩短、合并不同机制、抽样、压薄内容或拆分为多份。
4. **深度阻断自检**：每个核心单元是否覆盖完整实现面而非抽样？阅读范围是否与实际覆盖一致，是否漏读相关包/文件的大块实现？是否始终保持单份完整报告，并对所有单元维持完整深度而未因篇幅压薄或合并？

## 业务视角固定章节

业务视角 HTML 和 Markdown 都按以下顺序组织，并继承“深度与覆盖闸门”。以下章节、详细度与图表要求是现有产出基线，不得因新增架构视角而删减或弱化。章节内容完全条件性：真实代码中存在则详实呈现，不存在则写“代码范围内未发现”，绝不编造。

1. **一句话结论**：业务本质、入口与最终业务结果，用一条信息密度高的句子说明。
2. **阅读范围**：涉及仓库、代码来源、每个仓库实际版本标识、分析边界；多仓库逐一列出 `仓库名 @ 实际版本/ref`，工作区模式明确标注“行号与当前工作区一致”。
3. **术语表**：首次出现的业务黑话、缩写、状态码、外部系统名；每项集中解释一次。
4. **系统总览图**：按真实架构映射入口、核心处理、存储、外部依赖和异步路径；多仓库时画出仓库边界和经证据证明的跨仓库关系；概念角色不存在时说明，不套固定架构。
5. **实体关系图**：存在多个核心实体时必须绘制，展示关键字段、真实关联字段名及方向；涉及继承、实现、组合、聚合或依赖等类型关系时，按视觉规范使用 UML 记法；无可证明关联则说明。
6. **实体状态机**：每个有状态实体独立一张；无状态对象不强行画状态机。
7. **核心链路时序图**：每条真实核心链路独立绘制；取消、补偿、同步、绑定等只在代码存在时要求。无对应代码时明确说明。
8. **关键字段生命周期**：状态、batch ID、tracking number、外部单号、correlation/idempotency key 等核心字段从首次写入到终态。
9. **各模块深挖**：按可辨识的仓库归属组织真实存在的入口、核心、异步、外部依赖等概念角色；底座与扩展中的同名机制分别解释，只有代码证明共享行为时才合并陈述。
10. **方法速查表**：方法名、deep link、职责、字段变化、失败处理。
11. **状态流转对照**：实体、来源状态、目标状态、触发方法、前置条件、持久化/外部副作用、终态标记。
12. **上下游说明**：上游触发方、下游依赖、仓库归属、调用协议/方向、失败影响。
13. **设计意图补充**：只写图表难以表达的事务边界、幂等、顺序约束、反直觉分支、隐含约束；可在确有证据且有学习价值时插入轻量“设计亮点” callout。
14. **排障清单**：按现象组织，给出优先检查位置、可能原因、如何确认。

不要单独输出“证据与缺口”章节。分析范围、分支和文件数放在“阅读范围”；不确定性只在对应的结论、图注或设计意图旁用 `证据不足` 标签说明。

## 架构视角固定章节

架构视角不套用业务 ER、业务状态机、业务上下游或业务排障章节骨架，并继承“深度与覆盖闸门”。HTML 和 Markdown 必须按以下顺序组织；代码中不存在的机制写“代码范围内未发现”，不得为了完整性虚构插件、驱动、schema、缓存、迁移或状态机。

1. **一句话结论**：该系统/框架解决什么问题，核心设计如何分工。
2. **阅读范围**：涉及仓库、代码来源、每个仓库实际版本标识、分析边界与目标选择；多仓库逐一列出 `仓库名 @ 实际版本/ref`，工作区模式明确标注“行号与当前工作区一致”。
3. **术语表**：核心类型、概念、协议、配置名或约定。
4. **架构总览图**：真实入口、执行主干、核心层、基础设施/外部边界与装配关系；多仓库时画出仓库边界，以及经依赖、注册、实现、调用或改造证据证明的关系。
5. **核心抽象与类型关系图**：interface/trait/abstract class、struct/class 实现、组合、注入和注册关系；按视觉规范使用 UML 泛化、实现、组合、聚合、依赖和关联记法；没有可证明关系时明确说明。
6. **主干调用链时序图**：从真实入口 API/CLI/事件到执行底层，按阶段拆图，逐步展示参数、关键数据结构、返回和错误分支。
7. **关键数据结构与其构建/流转**：核心 request/context/options/AST/schema/plan/result 等真实类型的创建、转换、复制、缓存或销毁路径。
8. **核心机制与设计模式深挖**：按仓库归属分别讲解真实存在的回调、插件、责任链、中间件、工厂、注册表、依赖注入、缓存、并发或事务机制；说明原理、设计动机和扩展点；可在确有证据且有学习价值时插入轻量“设计亮点” callout。
9. **函数/方法速查表**：方法名、deep link、职责、关键结构变化、边界与错误处理。
10. **建议阅读路线**：从最小公开入口开始，按真实调用顺序给出文件/函数阅读路径与每一步的阅读目标。
11. **扩展点与自定义方式**：如何接入真实存在的 plugin/driver/callback/adapter/configuration 等扩展点；没有公开扩展点时明确说明。
12. **易踩坑与调试入口**：按源码阅读或调试症状组织，给出首个有诊断价值的入口、可验证条件和日志/断点位置。

若架构目标含有真实的状态机或状态驱动执行模型，可在第 7 或第 8 节增加状态图作为支持性图表；无状态实体或模型不得新增业务状态机章节。

## 架构视角图表密度与质量

架构视角的图表密度和视觉质量不得低于同等范围的业务视角。图不是装饰：每张图必须解释一种真实结构、机制、数据流或调用边界，并与对应文字深挖配套。

1. **基本图集**：每份架构报告至少包含架构总览图、核心抽象/类型关系 UML 图、关键数据结构构建/流转图；“关键数据结构与其构建/流转”不得只有文字。
2. **目标与机制专属图**：用户列出多个目标时，每个代码中真实存在的目标成为独立、可辨识的小节，至少配一张专属图和架构版五要素深挖。每个真实核心机制或主干也至少有一张专属图；代码范围内未发现实现时明确说明，不虚构图。
3. **图类型匹配机制**：调用顺序使用时序图；类型/实现/注入关系使用 UML 图；有分支或选择逻辑的机制使用流程/决策图；关键数据结构构造、转换、缓存或销毁使用生命周期/流转图。不得把性质不同的机制都塞进线性时序图，也不得把多个不同机制压成少数共享图。
4. **多仓库分别可读**：多仓库中每个具有独立核心子系统或机制的仓库各有其专属图，保留既有仓库/版本边界与跨仓库关系规则。
5. **图文配套**：核心机制深挖中的每个重要机制都有对应图；图展示结构、流程或选择，文字解释为何这样设计、边界、错误处理和扩展点。
6. **统一视觉质量**：所有图表复用同一套模板 SVG 构件与语义色，包含低饱和配色、圆角、最小 `12px` 图中文字、图例、足够留白、无标签重叠和正交布线；视角只能改变图表表达的事实，不能改变箭头、节点、泳道、字段胶囊或异常分组的视觉系统。

## 设计亮点 callout

`.highlight` 是可选的轻量说明，不是固定章节、不是质量门槛，也不得替代方法深挖、图表或证据。

- 仅用于代码能够直接支撑、对理解设计取舍或扩展边界有信息量的客观观察。
- 每个亮点必须在同一段中提供可回溯的 `file:line` 证据，并说明设计效果或代价；不确定时不标注。
- 使用克制：默认不出现；不得每节重复出现，不得把常规分层、命名或任意模式包装为亮点。
- 文案避免“优秀”“完美”“巧妙”等主观营销词，使用可验证的机制与后果描述。
- 业务视角仅放在“设计意图补充”或相关方法深挖附近；架构视角仅放在“核心机制与设计模式深挖”或相关方法深挖附近。

## 多仓库归属与关系

多仓库是默认分析行为，不需要额外输入。单仓库报告保持原有章节与图表密度，不添加无意义的边界或标签。

- 页首和阅读范围逐一列出每个仓库及其实际分析版本/ref；所有结论、方法、模块段落、图节点与图边以仓库标签、分组标题或图例可辨识归属。
- 仅在真实代码证明时呈现跨仓库关系，证据可来自 import/模块依赖、构建替换、注册、接口实现、调用、生成契约、注释或可验证的改造痕迹。无法证明时并列说明，不推断上游、fork、底座或扩展关系。
- 代码证明存在底座与扩展、fork 与改造版或上层依赖时，分别说明每个仓库新增、改动、覆盖或复用的对象与边界；同名机制分开讲，只有共享实现或调用证据存在时才合并说明。
- 总览图和关系图按仓库边界分组；时序图参与方和跨仓库消息标注 `仓库名 @ 版本`，并在跨边箭头上写明真实调用、实现、注册或数据传递动作。

## 业务视角核心方法深挖标准

每个真实核心方法必须以一个独立小节讲清以下五件事，缺一不可：

1. **做什么**：一句话职责，说明它在业务链路里的位置。
2. **执行顺序**：按实际分支和调用顺序描述关键步骤，不用“进行处理”之类空话。
3. **字段变化**：列出修改的实体字段、写入前后值或值来源、持久化位置。
4. **失败处理**：错误如何返回、是否重试、是否投递 MQ/任务、是否触发补偿/人工修复，失败时状态停在哪里。
5. **设计意图**：为什么要校验、拆分、延迟、复制字段或异步化；没有足够证据时标为 `代码推断` 或 `证据不足`。

方法块应包含：

```text
方法：<repo>::<package>.<symbol>
证据：<file:line>
职责：
执行顺序：
字段变化：
失败处理：
设计意图：
相关调用方 / 被调用方：
```

方法名本身是编辑器 deep link，使用 `.code-open target="_blank"` 呈现；不显示“打开代码”泛化文案、fallback 命令或折叠代码片段。

## 架构视角核心方法深挖标准

每个真实核心方法必须以独立小节讲清以下五件事：

1. **做什么**：该方法在系统主干或机制中的职责。
2. **执行顺序**：按真实分支、调用与构建顺序解释。
3. **关键数据结构变化**：说明参数、上下文、配置、抽象对象、计划或结果如何创建、转换、组合、缓存或传递。
4. **边界与错误处理**：说明 I/O、并发、事务、解析、配置或实现边界；错误如何返回、包装、忽略或重试。
5. **设计意图与扩展点**：解释该抽象/分层为何存在，及真实可替换、注册、注入或回调位置；证据不足时如实标注。

方法块应包含：

```text
方法：<repo>::<package>.<symbol>
证据：<file:line>
职责：
执行顺序：
关键数据结构变化：
边界与错误处理：
设计意图与扩展点：
相关调用方 / 被调用方：
```

方法名本身是编辑器 deep link，使用 `.code-open target="_blank"` 呈现；不显示“打开代码”泛化文案、fallback 命令或折叠代码片段。

## 模块深挖覆盖

入口、核心、异步、外部依赖是概念角色，不是固定架构层。仅覆盖代码中真实存在的角色：

| 概念角色 | 可识别对象 |
|---|---|
| 入口 | HTTP/gRPC/CLI/消息/定时入口 |
| 核心 | 规则、状态、事务、用例或服务实现 |
| 异步 | 消费者、任务、调度、发布者、回调 |
| 外部依赖 | DB、Repository、HTTP/RPC、MQ、缓存、文件或适配器 |

每个存在角色至少选择一个真实核心方法，并按五要素详解。不存在角色写“代码范围内未发现”，不凑数。

## 核心链路拆解标准

每条链路在图后按阶段逐段解释：

| 阶段 | 调用方法 | 输入与判断 | 写入/副作用 | 失败与下一步 | 证据 |
|---|---|---|---|---|---|

至少说明：

- 谁触发该链路，携带哪些关键标识。
- 每个关键方法的输入、关键校验、输出和字段变化。
- 事务、DB 写入和外部调用的先后顺序。
- 成功、可恢复失败、不可恢复失败和异步补偿的不同路径。
- 链路在多仓库间如何跨边界传递上下文。
- 时序图逐步展示：步骤编号、真实方法名、关键入参、字段写入或返回；成功/失败用 alt/else，重试/幂等/异步用独立虚线分组。

不要把“调用 A、调用 B、调用 C”当作链路解释。每一步必须说明业务意义和分支后果。

## 图与文字的一致性

- 图中的节点、状态、箭头、方法名必须来自证据账本。
- 图中省略了非核心步骤时，在图下注明“为可读性省略的步骤”及其代码位置。
- 单图超过 12 个参与方、20 条消息或阅读宽度明显失控时，拆为按阶段组织的多张图。
- 状态机不能绘制非法路径；未知转移不能用虚线伪装成事实。
- 关系图只画实际引用、持久化关联、显式映射或可追踪的调用关联。
- 多个核心实体存在时，ER 图必须覆盖所有实体；每个实体必须有真实关联边，或明确“代码范围内未发现实体关联”。
- UML 类型关系只在代码明确证明时使用：泛化/继承与接口实现采用空心三角，组合采用实心菱形，聚合采用空心菱形，依赖采用虚线开箭头，关联采用实线箭头。不得凭命名、目录或推测补画关系、基数或所有权。
- 每条有向关系使用独立 `<path marker-end="...">`；不得把多条关系压缩成只有末端箭头的折线。
- 写入 HTML 的 SVG 必须已是最终形态；不得依赖 JavaScript 改图或保留备用 SVG。
- 多仓库图的组件、类型、实体、泳道和跨仓库边均标注所属仓库；跨仓库边必须有对应证据，不能因包名相似、版本接近或目录结构相同推断关系。

## 排障清单格式

按读者看到的现象组织，而不是按模块文件名组织：

| 现象 | 优先看哪里 | 可能原因 | 如何确认 |
|---|---|---|---|

“优先看哪里”必须链接到第一个有诊断价值的 handler、状态写入、外部调用、MQ consumer、任务或 SQL/Repository 方法。可能原因只能列出代码可支持的条件、异常或缺失分支。

## 条件性阻断式生成前自检

任一“代码存在但未呈现”的项目均阻止写文件；“代码范围内未发现”是合法跳过结果：

### 业务视角

1. 已继承并通过“深度与覆盖闸门”：每条核心链路、实体和方法覆盖完整实现面，阅读范围与实际文件/符号覆盖一致；无论范围大小均保持单份完整报告，未因篇幅压薄或合并单元。
2. 14 个固定章节完整，缺失要素明确说明。
3. 多个核心实体存在时，ER 图覆盖所有实体并包含真实关联边。
4. 有状态实体均有状态机；无状态业务不造状态机。
5. 每条真实核心链路均有独立、详实时序图；不存在的链路已明确说明。
6. 时序图包含关键步骤、入参、字段写入/返回、真实分支、重试/幂等/异步。
7. 模块深挖覆盖存在的概念角色；所有真实核心方法答齐业务版五要素。
8. 出现类型继承、实现、组合、聚合、依赖或关联时，关系图使用正确 UML 记法；不存在时不为图表完整性补画。
9. 多仓库时，阅读范围、模块深挖、总览/关系/时序图均保留仓库归属；跨仓库关系只来自真实依赖、实现、调用、注册或改造证据。

### 架构视角

1. 已继承并通过“深度与覆盖闸门”：每个目标、主干和机制覆盖完整实现面，阅读范围与实际文件/符号覆盖一致；无论范围大小均保持单份完整报告，未因篇幅压薄或合并单元。
2. 12 个固定章节完整，且未混入业务 ER、业务状态机或业务上下游章节。
3. 核心抽象与类型关系图覆盖真实 interface/trait/abstract class、实现、组合、注入或注册关系；没有关系时明确说明。
4. 主干调用链时序图从真实入口展开，包含关键参数/数据结构、返回、错误和异步或并发边界（存在时）。
5. 关键数据结构的构建与流转可回溯且有专属图；不存在状态驱动模型时不造状态机。
6. 每个真实用户目标、核心机制或主干各有独立小节、专属图和架构版五要素深挖；有分支机制使用流程/决策图，未把不同机制压成少数共享时序图。
7. 核心机制深挖与方法速查表覆盖真实存在的设计模式和扩展点；所有核心方法答齐架构版五要素。
8. 建议阅读路线按真实调用顺序可执行；扩展点与自定义方式只描述代码证明的入口。
9. 类型关系图的 UML 记法、关系方向和标签均可回溯到真实代码；没有明确关系时不推断。
10. 多仓库的底座、扩展、fork、改造版或上层机制分别呈现，只有共享行为被代码证明时才合并说明。
11. 每张架构图在低饱和配色、圆角、最小 `12px` 字号、图例、标签无重叠、正交布线、留白和模板 SVG class 复用上不低于业务图，且无连线穿节点。

### 两种视角共用

1. 最终 HTML 由模板填充，SVG 静态最终化，脚本只含 scrollspy/lightbox。
2. 编辑器导航以方法名/明确对象名为 `.code-open target="_blank"` 链接，不显示泛化按钮文案或命令。
3. 证据不足仅在确实不确定处标记，图文删除任一侧后仍可独立理解主干。
4. “设计亮点”如存在，使用模板 `.highlight`，具备 file:line 证据且不替代正常章节；不存在时不强行添加。
5. `要求` 仅在护栏内被采纳：未删减任何固定章节、关系图、状态机、核心时序图、多仓库归属或静态离线交付规则；冲突部分在完成提示中透明说明。
